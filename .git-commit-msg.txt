fix(security): lock down image upload APIs (SSRF, object hijack, unscoped storage access)

Fixes from the 2026-09-27 image-upload audit:

- SSRF: getImageBuffer() in production docs export fetched any client-
  supplied http(s) URL. Now only fetches from this app's own S3 bucket
  host and validates the response is actually an image before embedding.
- Style baseImageKey could be set to any object key via PATCH /styles/:id
  with no scope/existence check, letting one style hijack another
  resource's file and read it back via the presigned base image URL. Now
  validated against styles/<id>/... scope + a real headObject() check,
  same pattern style-documents/style-sample-rounds already use.
- GET /storage/uploads/view-url and DELETE /storage/uploads accepted any
  objectKey with nothing but bare @Auth() - any logged-in user could read
  or permanently delete any object in the whole bucket. DELETE removed
  entirely (no caller used it); view-url now requires the key to match a
  known styles/purchase-orders prefix and that entity to still exist.
- /storage/uploads/presign issued a presigned PUT for any entityId with
  no existence check.
- Unified the image MIME allowlist (added webp/gif everywhere images are
  accepted, matching the sample-round upload).
- The advertised max upload size was only ever checked against a
  client-declared sizeBytes at presign time, which S3 presigned PUT can't
  enforce. Confirm endpoints now check the real uploaded object size and
  delete it if it's over the limit.
